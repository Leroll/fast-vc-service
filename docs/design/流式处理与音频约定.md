# 流式处理与音频约定

## 1. 音频流与分块

WebSocket 二进制消息可以是 PCM 数据块或一个原始 Opus 包；服务将其解码、累计，再按 `block_time` 取出推理块。客户端发送包与模型推理块不是一一对应关系。

[buffer.py](../../src/fast_vc_service/buffer.py) 在 `prefill_time < block_time` 时先补入指定时长的静音。prod.yaml 为 500 ms 推理块、375 ms 静音预填充，首块理论上再累计 125 ms 输入即可开始推理；这不是实测首包时延，也不包含模型执行、网络及播放等待。

正常结束信号会触发剩余缓冲处理，不足一个推理块的尾部补静音。异常断联和收包超时进入清理，不走正常结束的尾块补齐流程。

## 2. 采样率与数据表示

| 环节 | 含义 | 默认配置 / 协议行为 |
| --- | --- | --- |
| 客户端输入 | `sample_rate`，描述传入 PCM 或 Opus 解码后的采样率 | 协议缺省 16000 Hz |
| 模型前端 | `SAMPLERATE_IN`，缓冲重采样后的数据供 VAD、内容编码与音高处理 | prod.yaml 为 16000 Hz |
| 模型与后处理输出 | `SAMPLERATE_OUT`，与所选模型采样率一致 | tiny 配置为 22050 Hz |
| WebSocket 输出 | `sample_rate_out`，模型后处理完成后按需要再次重采样 | 缺省 16000 Hz；tiny 可显式请求 22050 Hz |

PCM 输入解码支持 16 / 24 / 32 位有符号整数；示例优先使用 16 位、小端、单声道。不要发送 WAV 文件头或浮点 PCM 并声明为整数。Opus 输入采样率由缓冲实现限制为 8000 / 12000 / 16000 / 24000 / 48000 Hz。

对外输出由路由转换为 int16 二进制 PCM，无 WAV 头；声道固定为 1。输出采样率按请求解释，不能沿用输入采样率猜测。模型输出采样率与协议输出采样率是两个不同参数。

具体协议字段见 [WebSocket API](../api_docs/websocket-api-doc.md)。

## 3. 上下文与模型窗口

[realtime_vc.py](../../src/fast_vc_service/realtime_vc.py) 将新音频追加到 Session 的滑动窗口。窗口包含内容编码器上文、SOLA 搜索/拼接区、当前块及右侧上下文。

内容编码器的上文长度由 `extra_time_ce` 控制；DiT 上文由 `extra_time_dit` 控制。编码后裁去两者差值，再进行长度对齐和条件拼接。配置要求前者大于后者。

音频帧数按 `FRAMERATE` 对齐，计算中存在取整；改变块长、上下文或帧率时需要同时检查输出长度和边界。VAD 与长静音状态会影响窗口更新和有声上下文的保留，不能仅以“每块独立转换”理解模型行为。

## 4. 后处理与延迟

推理顺序为 VAD、预处理、可选音高处理、语音转换、RMS 包络混合、SOLA 拼接及按需输出重采样。

`rms_mix_rate = 0` 更接近输入包络，`1` 保留推理包络。SOLA 对相邻输出进行对齐与交叉淡化；输出从模型生成的窗口中裁取，并非直接返回窗口末尾。

右侧上下文、SOLA 搜索与拼接区会增加算法等待。首包还受到预填充和首次推理影响，持续播放还受收发调度及客户端缓冲影响。评测必须区分这些因素，见[评测指南](../evaluation/README.md)。
